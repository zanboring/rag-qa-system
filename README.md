# RAG 知识库问答系统

一个**可评测、可部署、可插拔**的检索增强生成（RAG）知识库问答系统。

不是"跑通 demo"级别的项目：它有标注评测集与可复现的指标、有容器化部署方案、
有针对真实缺陷的修复记录，以及每个设计决策的取舍说明。

**RAG 全链路**：切片 → 向量化 → 检索 → 重排 → 组装 Prompt → 生成 → 溯源

## 核心能力

| 能力 | 说明 |
| --- | --- |
| **全链路可插拔** | 向量化 / 向量库 / 大模型三层各自独立可换，改环境变量即可，默认零依赖可离线运行 |
| **可评测** | 54 条标注样本 + 4 类指标（检索 / 生成 / 拒答 / 延迟），配套评测集自检门禁，指标可复现 |
| **可部署** | Dockerfile + docker-compose 一键启动，向量库可持久化，非 root 运行，内置健康检查 |
| **可溯源** | 每个回答返回引用来源、相似度、置信度与关键词高亮片段 |
| **可诊断** | 评测报告自动判断瓶颈在召回侧还是排序侧，而非只罗列数字 |

**零依赖起步**：`clone → pip install → uvicorn` 即可运行，不需要 GPU、不需要网络、
不需要 API Key。默认后端的组合是字符 n-gram 哈希 + 内存向量库 + mock 生成。

## 评测体系

这是本项目与"demo 级 RAG"最大的区别：**每个优化都有数据支撑，而不是凭感觉调参**。

### 评测集设计

`eval/corpus/` 下 16 篇 RAG 领域技术笔记，`eval/golden_set.jsonl` 中 54 条标注样本。

设计上有四个刻意的选择：

1. **主题高度邻近**。语料全部围绕 RAG 技术栈（切片、embedding、向量库、重排、评测……），
   存在大量"看起来都相关"的干扰项。如果换成 16 篇互不相关的文档，所有后端都能拿满分，
   评测就失去了区分度。

2. **按内容而非 chunk_id 标注**。相关性判定用「文档名 + 必须包含的关键串」，
   不硬编码 `doc_id:chunk_index`。因为 chunk_id 依赖切片参数，一旦调整 chunk_size，
   硬编码的标注会全部失效——用内容标注则换切片策略后依然有效。

3. **包含无答案样本**。4 条样本的问题在知识库中确实没有答案（如"Milvus 单节点最多支持多少向量"），
   考察系统**拒答**能力。这类样本最容易被忽略，但恰恰是防幻觉的关键。
   它们不参与检索指标计算，单独用正确拒答率衡量——因为"不该乱答"和"能不能找到"是两种能力。

4. **评测集自检门禁**。`validate_set.py` 会校验每条标注的关键串是否真实存在于对应语料。
   标注写错会导致该样本永远判不中、指标被永久压低，而报告上完全看不出来。
   这个门禁在开发过程中实际拦下了一处错误标注。

### 指标口径

| 类别 | 指标 | 衡量什么 |
| --- | --- | --- |
| 检索 | Hit@K、Recall@K、Precision@K、MRR、nDCG@K | 能不能召回、排得好不好 |
| 生成 | 关键词覆盖、上下文覆盖（规则）| 答案/上下文对标准答案要素的覆盖度 |
| 生成 | Faithfulness、Answer Relevancy（LLM 裁判）| 有没有幻觉、是否切题 |
| 拒答 | 正确拒答率、误拒率 | 无依据时是否敢说"不知道" |
| 性能 | P50 / P95 延迟 | 用户实际体感 |

召回与排序分开看是刻意的：**Recall 决定上限，MRR/nDCG 决定体验**。
如果 Hit@5 高但 MRR 低，说明正确片段召回了却排在后面，该优化重排而非切片。

### 实测结果

配置：hash embedding + 内存向量库 + mock 生成，54 条样本，Top-K=5。
两个正交变量：**哈希维度**（代表表示能力）× **是否开启重排**（代表排序质量）。

| 配置 | Hit@1 | Hit@3 | Hit@5 | Recall@5 | MRR | nDCG@5 | P50 延迟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| hash256，无重排 | 0.2800 | 0.5400 | 0.5800 | 0.5300 | 0.4090 | 0.4495 | 2.3 ms |
| hash256，开启重排 | 0.4400 | 0.6200 | 0.7000 | 0.6500 | 0.5403 | 0.5798 | 3.1 ms |
| hash4096，无重排 | 0.6800 | 0.8800 | 0.9200 | 0.8900 | 0.7790 | 0.8092 | 30.9 ms |
| **hash4096，开启重排** | **0.7400** | **0.9400** | **0.9600** | **0.9300** | **0.8283** | **0.8576** | 31.7 ms |

两个可以直接引用的结论：

**1. 表示能力是检索的第一瓶颈。**
仅把哈希维度从 256 提到 4096——不换模型、不改检索算法——MRR 从 0.409 提升到 0.779
（**+90%**），Hit@5 从 0.58 提升到 0.92。

原因很明确：hash embedding 把字符 3-gram 哈希到固定数量的桶里，桶数不足时不同 n-gram
互相碰撞，向量区分度下降。**这也说明：当表示能力不足时，优化检索算法基本是徒劳的**——
正确片段压根没被正确表示出来，再好的排序也无从挽救。

**2. 排序优化的收益小于表示能力的收益。**
hash4096 不开重排（MRR 0.779）已经明显超过 hash256 开重排（MRR 0.540）。
重排能在既定表示下把最相关的片段提前（在 hash256 上 Hit@1 提升 57%），
但无法弥补表示本身的信息损失。

**这决定了优化优先级：先解决表示，再优化排序。**

代价方面：维度从 256 提到 4096，P50 延迟从 2.3 ms 升到 30.9 ms——
向量距离计算量随维度线性增长。这是典型的"质量换成本"权衡，
实际选型需结合检索频率与延迟要求，或改用 ANN 索引把高维检索的成本压下来。

按难度分层（hash4096 + 重排，实际报告数据）：

| 难度 | 样本数 | MRR | nDCG@5 |
| --- | --- | --- | --- |
| easy | 9 | 0.9444 | 0.9590 |
| medium | 27 | 0.8056 | 0.8378 |
| hard | 14 | 0.7976 | 0.8308 |

> **关于基线的说明**：以上全部是 hash embedding 的数据。它的本质是**词形匹配而非语义匹配**
> （见 `app/embedder.py`），对同义改写的泛化能力很差——即使 Hit@5 已达 0.96，
> 也是这种表示方式的上限附近。换成 BGE 等语义模型后，泛化能力会进一步改善。
> **报告指标时必须标明所用后端**，否则"Hit@5 = 0.58"会被误读成"这个系统的检索能力"，
> 而它实际上只是"某一个 embedding 后端的检索能力"。

### 怎么复现

```bash
python -m eval.validate_set                       # 第一步：先自检评测集
python -m eval.run_eval                           # 跑基线，自动对比重排开关
python -m eval.run_eval --hash-dims 256,4096      # 对比哈希维度（表示能力）的影响
python -m eval.run_eval --embedding bge           # 换 BGE（需 pip install sentence-transformers）
python -m eval.run_eval --llm glm4                # 接真实模型，产出忠实度等指标
```

产出：`eval/results/report.md`（汇总报告）、`detail_*.json`（逐样本明细）。 

**关于裁判**：未配置 `JUDGE_API_KEY` / `ZHIPU_API_KEY` 时自动降级为规则裁判，
此时忠实度与答案相关性显示为 `n/a`。这是刻意的——这两项需要语义理解，
用关键词规则冒充会得出看似合理、实则误导的数字，**宁可不报也不报假的**。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/documents` | 上传文档（切片 + 向量化 + 入库） |
| POST | `/documents/batch` | 批量上传（单篇失败不影响整体，上限 50 篇） |
| POST | `/query` | 提问（检索 + 可选重排 + 生成 + 溯源） |
| GET | `/documents` | 分页列出文档（按入库时间倒序） |
| GET | `/documents/{doc_id}` | 获取单个文档元数据 |
| PUT | `/documents/{doc_id}` | 更新文档（`name`/`text` 至少传一个） |
| DELETE | `/documents/{doc_id}` | 删除文档及其全部向量片段 |
| GET | `/health` | 健康检查 + 当前后端与配置回显 |

`/query` 响应字段：

```json
{
  "answer": "快速排序的平均时间复杂度是 O(n log n) [1]……",
  "sources": [
    {
      "doc_name": "算法笔记.md",
      "chunk_index": 0,
      "score": 0.91,
      "confidence": 0.62,
      "snippet": "**快速排序**是一种分治算法……"
    }
  ],
  "confidence_avg": 0.62,
  "top_score": 0.91
}
```

- `score`：原始相似度（余弦值），绝对量纲。
- `confidence`：相对归一化 `score / Σscores`。**注意它有已知局限**：
  单片段时恒为 1.0，均匀分布时偏低，因此只能作为相对集中度参考，
  不能直接当"答案可信度"用（详见 `app/rag.py` 中的说明）。
- `snippet`：前 120 字符片段预览，命中关键词用 `**...**` 包裹（大小写不敏感）。

## 部署

### 配置项

全部通过环境变量控制，模板见 `.env.example`。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `EMBEDDING_BACKEND` | `hash` | `hash`（零依赖）/ `bge`（本地）/ `zhipu`（云端） |
| `VECTOR_BACKEND` | `memory` | `memory`（内存）/ `chroma`（需额外安装） |
| `LLM_BACKEND` | `mock` | `mock`（假模型）/ `ollama`（本地）/ `glm4`（云端） |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | `500` / `50` | 切片粒度 |
| `CHROMA_PATH` | 空 | 向量库落盘路径，**留空则重启丢数据** |
| `ZHIPU_API_KEY` | 空 | 使用 `glm4` / `zhipu` 后端时必填 |

启用 ChromaDB 持久化：

```bash
pip install -r requirements-chroma.txt
export VECTOR_BACKEND=chroma
export CHROMA_PATH=./chroma_db
```

### 数据持久化

| 数据 | 存储位置 | 重启后 |
| --- | --- | --- |
| 向量与片段元数据 | 向量库（`CHROMA_PATH`） | 持久化模式保留 |
| 文档注册表 | 由向量库**启动时反向重建** | 自动恢复 |

文档注册表刻意不单独持久化，而是启动时从向量库的片段 metadata 反向聚合重建
（`app/main.py` 的 `_restore_documents`）。这样**向量库是文档元数据的单一事实来源**，
从根本上避免了"两份数据各写各的"导致的不一致——否则一旦只持久化了向量，
重启后会出现"检索能命中，但文档列表是空的"这种让用户以为数据丢了的状态。

代价是 `created_at` 等文档级字段随每个片段冗余存储。

### 上线检查清单

- [ ] `VECTOR_BACKEND=chroma` 且 `CHROMA_PATH` 指向挂载卷
- [ ] `ZHIPU_API_KEY` 通过环境变量注入，**不写进镜像、不提交仓库**
- [ ] `curl /health` 确认 `backends` 与 `vector_persistent` 符合预期

- [ ] 按实际语料量评估：内存向量库的暴力检索在 10 万片段内够用，超出需换 ANN 索引

## 设计决策与取舍

### 架构

| 模块 | 核心概念 | 取舍 |
| --- | --- | --- |
| `chunker` | 固定长度 + 重叠切片 | 为什么要有重叠：避免一句话被从中间切断，丢失跨边界语义 |
| `chunker` | 边界优先切片 `chunk_text_smart` | 段落 > 换行 > 中文句末 > 英文句末（带空白锚点）> 分句 > 空白；找不到边界回退硬切；`MIN_KEEP_RATIO=0.5` 防止切成超小块 |
| `embedder` | 文本 → 高维向量 | 默认 hash embedding：零依赖可离线；生产换 BGE / 智谱 |
| `vectorstore` | 余弦相似度 Top-K | 内存 O(n) 暴力 vs ChromaDB/Milvus 的 ANN 近似检索 |
| `reranker` | RRF 融合语义 + 词法两路排序 | 只依赖名次、无需分数归一化；生产可换 cross-encoder |
| `llm` | 大模型生成 | 本地 Ollama（隐私 / 免费）vs 云端 GLM-4（效果 / 便捷） |
| `rag` | 检索增强 + 溯源 | 给 LLM「参考资料」减少幻觉，回答可溯源 |

### 工程决策

| 决策 | 理由 |
| --- | --- |
| **评测集用内容标注而非 chunk_id** | 换切片参数后标注不失效，评测集可长期复用 |
| **召回指标与排序指标分开统计** | 混在一起会互相掩盖问题，无法定位是召回漏了还是排序差了 |
| **无答案样本单列拒答指标** | "不该乱答"与"能不能找到"是两种能力，混算会互相抵消 |
| **无 Key 时不产出生成绩效指标** | 用规则冒充语义判断会得到误导性数字，宁可标 `n/a` |
| **mock 后端下拒答指标标 `n/a`** | mock 的答案既不构成作答也不构成拒答，强行计算会得出"拒答率与误拒率同时为 100%"的矛盾结论 |
| **上传/更新改为受控并发向量化** | 串行 await 让耗时随片段数线性增长；`Semaphore(8)` 兼顾吞吐与限流风险 |
| **更新走「先算向量再删旧」** | 先删后算时，embed 一旦失败会导致文档永久丢失 |
| **批量上传单篇失败不抛 500** | 记入 `failed` 数组并返回 200，调用方一次能传多篇而不必重试整批 |
| **默认后端零依赖** | clone 下来装完基础依赖就能跑通、能跑测试，不必先下载几百 MB 依赖 |

## 踩过的坑

以下都是开发过程中真实遇到并修复的问题，附原因分析与修复方式。

### 1. ChromaDB 默认距离度量不是余弦

**现象**：切换到 Chroma 后，`score` 字段的数值与内存库对不上，基于 score 计算的
`confidence` 也失真。

**原因**：Chroma 创建 collection 时默认使用 L2（欧氏距离），而本项目的内存库用余弦相似度。
代码里写的是 `score = 1 - distance`，在 L2 下这个式子的含义是错的：

```
L2 距离 = 0.5  ⇒  实际余弦相似度 ≈ 0.875，而 1 - 0.5 = 0.5
```

两者数值不等。更隐蔽的是**排序结果依然正确**（因为归一化后 L2 与余弦单调等价），
所以问题不会在功能测试里暴露，只会让分数失去绝对量纲。

**修复**：创建 collection 时显式指定 `metadata={"hnsw:space": "cosine"}`，
此时 `distance = 1 - 余弦相似度`，`1 - distance` 才真正等于余弦相似度。

### 2. 同步 API 阻塞事件循环

**现象**：查询期间的并发请求被排队，吞吐上不去。

**原因**：Chroma 的 Python 客户端是同步阻塞 API，直接在 `async def` 里调用会卡住事件循环，
整个服务在查询期间无法处理其它请求。

**修复**：所有 Chroma 调用统一包进 `asyncio.to_thread` 卸载到线程池。

### 3. 连接池从不释放

**现象**：反复创建管道（测试、重启）时资源占用持续累积。

**原因**：`ZhipuEmbedder` / `OllamaLLM` / `GLM4LLM` 各自持有 `httpx.AsyncClient` 以复用连接，
但**从来没有关闭过**，连接会一直驻留到进程退出。

**修复**：为各后端增加 `aclose()`，并在 FastAPI 的 lifespan 关闭阶段统一调用。

### 4. 更新文档时先删后写会丢数据

**现象**：网络抖动时更新文档，旧内容没了、新内容也没写上。

**原因**：原实现是"删除旧片段 → 逐条 embed → 写入新片段"。`embed` 是可能失败的外部调用，
一旦中途抛错，旧数据已经删除、新数据尚未写入，文档永久丢失。

**修复**：改为"先算完全部新向量 → 再删旧 → 再写入"，把失败窗口收窄到只读操作。

### 5. `1 - L2距离` 当相似度的连锁影响

项目里曾用 `1 - distance` 转换 Chroma 的距离。虽然排序没错，但它会让
`confidence = score / Σscore` 这个下游计算失去意义——因为分数不再处于余弦量纲。
这类"能跑通但数值错"的问题最难靠功能测试发现，**只能靠跨后端的一致性评测暴露**。

**修复**：统一余弦空间（见问题 1），并在评测中对比不同后端的指标是否可比。

### 6. 置信度定义本身的局限

`confidence = score / Σscore` 的实际含义是"该片段在 Top-K 中的相对占比"，
而不是"这个答案有多可信"。它有两个反直觉性质：

- **单片段时恒为 1.0**：只召回一条时，无论其相似度是 0.9 还是 0.05，归一化后都是 1.0。
- **均匀分布时偏低**：多个片段分数接近时每项接近 1/n，看似"低置信"，
  但这可能恰恰是"多条片段都同样相关"。

**处理**：保留该公式（向后兼容），但在代码中明确标注局限，并在文档中说明
正确的拒答判据应组合绝对分数阈值、Top-1/Top-2 分差、多片段一致性。

### 7. 关键词高亮的子串重复包裹

**现象**：查询"快速排序"时，片段中的"排序"被二次包裹，出现 `**快速**排序**` 这样的破损标记。

**原因**：旧实现依次对每个关键词调用 `re.sub`，长的关键词先替换后，
其内部的子串又会被短关键词再次匹配到。

**修复**：合并为单条 alternation 正则，并把关键词按长度降序排列，长关键词优先匹配。

## 已知限制与演进方向

诚实地列出当前的不足，以及各自的解决路径：

**检索质量**
- 默认 hash embedding 是词形匹配而非语义匹配，仅用于离线验证；接 BGE 后指标会显著改善
- 内存向量库为 O(n) 暴力检索，10 万片段内可用，更大规模需换 HNSW/IVF 索引
- 重排目前是零依赖的 RRF 词法融合，可升级为 cross-encoder（如 bge-reranker）

**切片**
- 固定长度 + 边界优先已够用，但语义切片（按相邻句子相似度突变处断开）质量更好
- 尚未支持按 Markdown 标题层级切分，结构化文档未充分利用其结构信息

**数据与并发**
- 文档注册表在内存中，多副本部署时各实例状态不共享，需引入数据库或共享缓存
- 关键词抽取为按停用词的零依赖实现，接入 jieba / HanLP 可提升中文切分质量
- 无鉴权机制，生产需增加 API Key / OAuth 与按用户隔离的知识库空间

**评测**
- 54 条样本规模偏小，指标置信区间较宽；扩充到数百条能更稳定地反映差异
- 语料集中在 RAG 技术领域，缺少长文档、表格、代码等异构内容的评测
- 裁判指标依赖外部 API，未做人工标注一致性校验（建议抽 30 条人工核对）

**工程**
- 未接入可观测性（结构化日志、指标上报、链路追踪），生产排查依赖日志检索
- 缓存层缺失：相同问题的重复查询会走完整链路，可加 Redis 缓存
- 增量索引与整库重建未实现，文档批量更新只能逐篇走 PUT

**当前验证状态（如实标注）**
- Dockerfile 与 docker-compose.yml 已完成，YAML 语法已校验通过
  （`services: api` / `volumes: chroma_data` 解析正常）；
  但开发本机未安装 Docker，**镜像构建与容器启动未经实测**，首次部署前请先本地 `docker compose up` 验证
- **BGE 等语义 embedding 的对比指标尚未产出**：`sentence-transformers`
  （含 torch，约数百 MB）安装未完成。评测框架已支持 `--embedding bge`，
  依赖装好后可直接补跑，命令见上文「怎么复现」
- 因此上文所有指标均来自 hash embedding。它能证明链路正确与相对趋势，
  **但不能代表语义模型的效果上限**
