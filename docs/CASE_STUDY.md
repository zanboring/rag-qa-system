# 案例：从"能跑"到"能证明"——一次完整的 RAG 调优过程

这份文档记录一次真实、可复现的调优流程：把一个能跑通的 RAG 系统，通过**评测驱动**
的方式诊断出瓶颈、验证优化效果，并给出可引用的数据。

所有步骤都可以照着复现，语料与评测集都在仓库里。

---

## 1. 目标与起点

**起点**：系统功能完整（上传、检索、生成、溯源、批量、分页都可用），45 个测试通过。

**问题**：除了"能跑"，没有任何证据说明它**效果如何**。

具体来说，以下问题此时都回答不了：

- 检索质量到底怎么样？命中率是多少？
- 调 `chunk_size` 有用吗？该往大调还是往小调？
- 重排开了会不会更好？好多少？
- 系统会不会在知识库里没有答案时胡编？

没有这些数据，所有优化都是凭感觉。**而"凭感觉优化"恰恰是 RAG 项目最容易走弯路的地方**——
比如效果不好时第一反应是换更大的生成模型，但真实瓶颈往往在检索。

---

## 2. 建立评测基线

### 2.1 先让评测集本身可信

评测集很容易写错，而且写错之后**报告上看不出来**——只会表现为"系统效果差"，
把时间浪费在调代码而不是修标注上。

所以第一步不是跑评测，而是校验评测集：

```bash
python -m eval.validate_set
```

输出：

```
语料文档数：16
评测样本数：54
  类型分布：{'single_hop': 39, 'numeric': 6, 'comparison': 4, 'multi_hop': 1, 'unanswerable': 4}
  难度分布：{'easy': 9, 'medium': 27, 'hard': 18}
  无答案样本：4 条（考察拒答能力）
  全部语料文档均被标注覆盖
------------------------------------------------------------
校验未通过，发现 1 个问题：
  - [q27] answer_keywords 关键词在标注文档中找不到：'倒数'
```

自检确实拦下了一处错误：`q27` 标注的关键词 `'倒数'` 在对应语料中并不存在。
如果不修，这条样本会永远判不中，静默拉低整体指标。修正后重新校验通过。

### 2.2 跑基线

```bash
python -m eval.run_eval
```

这一步同时对比"关闭重排"和"开启重排"两组配置：

```
=== 评测配置：hash+memory+mock+rerankoff ===
  完成：MRR=0.4090 nDCG@5=0.4495 Hit@5=0.5800 P50=2.1ms
=== 评测配置：hash+memory+mock+rerankon ===
  完成：MRR=0.5403 nDCG@5=0.5798 Hit@5=0.7000 P50=2.9ms
```

---

## 3. 诊断：瓶颈在哪一环

拿到基线数据后，报告里的自动诊断给出了判断：

```
- Hit@5 (0.58) 与 MRR (0.41) 较为接近，召回与排序表现均衡
- Hit@1 (0.28) 不到 Hit@5 的一半，首位答案不可靠 → 建议开启重排，或引入 cross-encoder 做精排
```

这个判断依据的是**指标之间的关系**，而不是单个数字的高低：

| 观察 | 含义 | 优化方向 |
| --- | --- | --- |
| Hit@5 低（< 0.5） | 正确片段压根没被召回 | 召回侧：切片粒度、embedding 能力、top_k |
| Hit@5 高但 MRR 低 | 召回了，但排得靠后 | 排序侧：重排策略 |
| Hit@1 ≪ Hit@5 | 用户第一眼看不到答案 | 重排，或提升精排质量 |
| Recall@5 > Hit@5 | 同一问题需要多片段才能答全 | top_k 偏小 |

本次的情况是第三种：**Hit@5 有 0.58，但 Hit@1 只有 0.28**。
正确片段大多被捞回来了，只是没排到第一位。这明确指向排序问题。

---

## 4. 验证优化：RRF 重排

既然瓶颈在排序，就开重排验证。系统的重排实现是 RRF（Reciprocal Rank Fusion），
融合"向量语义排序"和"词法重叠排序"两路信号——**不引入任何新模型，零依赖**。

对比结果：

| 指标 | 关闭重排 | 开启重排 | 变化 |
| --- | --- | --- | --- |
| Hit@1 | 0.2800 | **0.4400** | +57% |
| Hit@3 | 0.5400 | 0.6200 | +15% |
| Hit@5 | 0.5800 | 0.7000 | +21% |
| MRR | 0.4090 | **0.5403** | +32% |
| nDCG@5 | 0.4495 | **0.5798** | +29% |
| P95 延迟 | 2.3 ms | 3.1 ms | +0.8 ms |

**收益最大的正是 Hit@1（+57%）**，与诊断结论完全吻合：重排解决的就是"排序"问题。
代价是 P95 延迟增加 0.8 毫秒（多召回 3 倍候选），在总延迟里可以忽略。

分难度看，重排在最难的样本上收益依然明显：

| 难度 | 样本数 | 关闭重排 MRR | 开启重排 MRR |
| --- | --- | --- | --- |
| easy | 9 | 0.6481 | 0.7778 |
| medium | 27 | 0.3623 | 0.5302 |
| hard | 14 | 0.3452 | 0.4071 |

---

## 5. 更深一层：表示能力才是真正的瓶颈

重排确实有效。但诊断里还有一条信息值得继续追问：在 hash256 下，
**即使开启重排，Hit@5 也只有 0.70**——意味着约 30% 的问题里正确片段压根没被召回，
重排再强也无从下手。

这说明瓶颈在更靠前的环节。为了定位，做一个"不引入任何模型"的对照实验：
把 hash embedding 的**向量维度**从 256 提到 4096，其他一切保持不变。

| 配置 | Hit@5 | MRR | nDCG@5 | P50 延迟 |
| --- | --- | --- | --- | --- |
| hash256，无重排 | 0.5800 | 0.4090 | 0.4495 | 2.3 ms |
| hash256，开启重排 | 0.7000 | 0.5403 | 0.5798 | 3.1 ms |
| hash4096，无重排 | **0.9200** | **0.7790** | **0.8092** | 30.9 ms |
| hash4096，开启重排 | **0.9600** | **0.8283** | **0.8576** | 31.7 ms |

结果相当反直觉：**只改维度这一个参数，MRR 就从 0.409 涨到 0.779（+90%）。**

原因不难解释：hash embedding 把字符 3-gram 哈希进固定数量的桶。
当桶数不足以容纳实际的 n-gram 种类数时，大量不同的 n-gram 碰撞到同一桶，
向量的区分度被抹平。256 维对这个语料规模而言明显偏小。

对调优更有价值的是这一组对照：

| | MRR |
| --- | --- |
| hash4096，**不开**重排 | 0.7790 |
| hash256，**开**重排 | 0.5403 |

**提升表示能力带来的收益，远大于优化排序带来的收益。**

这直接决定了优化优先级：表示能力不足时，应该先换或调 embedding；
在表示能力不足的前提下去调重排、调 top_k、换更大的生成模型，
都是在做低杠杆的事——投入不小，天花板却由表示能力锁死了。

代价同样明确：延迟从 2.3 ms 涨到 30.9 ms（维度高 16 倍，向量距离计算量随之线性增长）。
质量与延迟的权衡要结合业务延迟要求来定，或者改用 ANN 索引把高维检索的成本压下来。

## 6. 失败案例分析

只看总体指标会漏掉细节。报告里列出了最差的样本，其中一条很值得分析：

| 样本 | 难度 | MRR | 召回文档 | 说明 |
| --- | --- | --- | --- | --- |
| q05 | easy | 0.0000 | 14-ragas-judge.md, 02-chunking-strategy.md, 01-rag-overview.md | 完全未命中 |

`q05` 的问题是"切片时为什么要在相邻块之间保留重叠？"，标注的正确答案在
`02-chunking-strategy.md` 里。Top-5 里虽然召回了这篇文章，但**召回的是错误的片段**
（不包含答案内容），因此判定为未命中。

原因分析：这条被标为 `easy`（人来看确实简单），但对 hash embedding 来说是**困难样本**。
语料中大量文档都包含"切片""重叠""分块"这类词汇，
而 hash embedding 只能做字符 n-gram 的**词形匹配**，
无法理解"为什么需要重叠"与"重叠率取多少"这两段话的语义差异。

这暴露的是**基线的根本限制**，而不是代码缺陷：

> hash embedding 的设计目标是"零依赖、可离线、结果确定"，用于验证链路和跑测试。
> 它不是语义模型，用它跑出的检索指标不能代表真实系统上限。

这也解释了为什么报告的每个配置行都必须标明 embedding 后端——
否则"Hit@5 = 0.58"会被误读成"这个 RAG 系统的检索能力"。

## 6. 复盘：如果重来一次

### 做对了的

1. **先建评测再优化**。如果直接上手调参，很可能会去改 `chunk_size` 或换生成模型，
   而真实瓶颈在排序——时间和精力都会浪费在错误的方向上。

2. **评测集自检前置**。写作时就拦下了一处标注错误。如果没做校验，
   这个错误会一直存在，且完全不可见。

3. **召回与排序指标分开**。这是能得出"Hmm 瓶颈在排序"这个结论的前提。
   如果只报一个综合分数，诊断就无从谈起。

4. **指标不可用时如实标注**。没有配置裁判模型 API Key 时，
   忠实度与答案相关性显示为 `n/a`，而不是用关键词覆盖率冒充。
   用规则指标冒充语义判断会得到看起来合理、实际误导的数字。

### 下次会改进的

1. **尽早接入真实 embedding**。hash embedding 作为基线能验证链路，
   但把它当作性能基线会产生误导。应该一开始就跑两组（hash / BGE）作为参照。

2. **评测集规模偏小**。54 条样本，单条样本对指标的影响可达 2 个百分点，
   置信区间偏宽。扩充到 200 条以上才能更稳定地识别小幅改进。

3. **补充异构内容**。当前语料全是结构规整的 Markdown 技术笔记，
   缺少长文档、表格、代码块等形态。真实场景中这些内容对切片策略的要求完全不同。

4. **引入人工标注校验**。裁判模型有已知偏差（位置偏好、长度偏好、自我偏好），
   应当抽 30 条人工核对，测出裁判与人工的一致率，否则裁判指标的可信度无从判断。

---

## 8. 这次调优沉淀下来的结论

可以直接在面试中引用：

- **修表示能力的收益 > 调排序的收益**。仅把 hash 维度从 256 提到 4096，
  MRR 提升 **90%**（0.409 → 0.779）；而开启重排在 hash256 上只把 MRR 提到 0.540。
  且 hash4096 **不开**重排（0.779）已经超过 hash256 **开**重排（0.540）。
  所以优化顺序应当是"先表示、后排序"——反过来做会事倍功半。

- **RRF 重排在零模型依赖下把 Hit@1 提升 57%**（0.28 → 0.44），MRR 提升 32%，
  代价是 P95 延迟 +0.8 ms。它适合"召回尚可、排序偏弱"的场景，
  但无法弥补表示能力本身的信息损失。

- **每一次质量提升都要量出代价**。维度 256 → 4096 让 P50 延迟从 2.3 ms 升到 30.9 ms
  （距离计算量随维度线性增长）。不给代价的"效果提升"在工程上无法决策。

- **诊断瓶颈靠的是指标之间的关系，不是单个数字**。
  `Hit@5 高 + MRR 低` 指向排序问题，`Hit@5 低` 指向召回问题。
  这个判断逻辑已经固化进评测脚本的自动诊断中，而不是靠人肉看表。

- **评测集本身需要被评测**。用内容包含关系（而非 chunk_id）标注，
  使评测集在调整切片参数后依然有效；用自检门禁保证标注正确，
  否则标注错误会静默污染全部指标，且从报告上完全看不出来。

- **基线数据必须标明所用后端**。hash embedding 的词形匹配能力与 BGE 的语义匹配
  不在一个量级，不加标注的数字会被错误解读成"系统的能力"，
  而它实际上只是"某一个后端的能力"。

## 附：完整复现命令

```bash
# 1. 安装依赖
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt

# 2. 校验评测集（必做，避免标注错误污染指标）
.venv/Scripts/python -m eval.validate_set

# 3. 跑基线评测（hash + mock，自动对比重排开关）
.venv/Scripts/python -m eval.run_eval

# 4. 换 BGE embedding 对比语义检索质量（需额外安装）
.venv/Scripts/pip install sentence-transformers
.venv/Scripts/python -m eval.run_eval --embedding hash,bge

# 5. 接真实模型评测生成质量（需 API Key）
set ZHIPU_API_KEY=你的Key
.venv/Scripts/python -m eval.run_eval --llm glm4

# 6. 查看报告
#    eval/results/report.md          汇总报告
#    eval/results/detail_*.json      逐样本明细
```
