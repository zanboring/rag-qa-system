# RAG 提示词结构与上下文组织

检索完成后，需要把片段组织成提示词交给大模型。这一步看似只是字符串拼接，但对答案质量的影响相当大。

## 三段式结构

一个稳健的 RAG 提示词包含三部分：

**1. 系统指令（System）**

定义模型的行为约束。核心要素包括：

- 角色定位："你是一个严谨的知识库问答助手"
- 依据约束："仅依据下面提供的参考资料回答问题"
- 引用要求："尽量标注引用来源编号"
- 拒答规则："如果资料不足以回答，明确说明「资料中未找到相关信息」，不要编造"

其中**拒答规则是最关键的一条**。如果不明确授权模型说"不知道"，模型倾向于强行给出一个听起来合理的答案，这正是 RAG 场景下幻觉的主要来源之一。

**2. 参考资料区（Context）**

每个片段应当带有可识别的来源标记，典型格式：

    [1] 来源《文档名》片段0：
    <片段正文>

    [2] 来源《文档名》片段3：
    <片段正文>

编号让模型可以在答案中用 `[1]` 这样的形式引用，也让前端能把引用映射回原文位置，实现可溯源。带上文档名和片段序号，还能在排查问题时快速定位是哪个片段导致了错误答案。

**3. 用户问题（Query）**

放在最后。把问题放在参考资料之后有两个好处：一是符合"先给材料再提问"的自然阅读顺序；二是对部分模型而言，靠近生成位置的内容影响力更大，问题放在末尾有助于模型紧扣提问。

## 片段的组织顺序

一个常被忽略的细节是**片段的排列顺序**。研究表明大模型对上下文存在位置偏好：位于开头和结尾的信息更容易被利用，中间部分容易被忽略（俗称"迷失在中间"）。

因此有两个实用技巧：

- **把最相关的片段放在最前**（或最后），而不是随意按检索顺序排列。
- **总上下文不宜过长**。塞入 20 个片段并不比 5 个更好，反而会稀释关键信息、增加成本、提高被无关内容干扰的概率。

经验做法是 top_k 取 3 到 5，配合重排序保证这 3 到 5 条确实是候选中最好的。

## 上下文去重

当切片存在重叠，或同一文档的多个片段被同时召回时，参考资料里会出现大量重复内容。重复内容会带来两个问题：占用宝贵的上下文窗口；让模型误以为该信息被多次强调而过度采信。

去重策略有两类：

- **内容级去重**：比较片段文本的相似度（如 n-gram 重叠率），超过阈值则只保留一条。
- **来源级控制**：同一文档最多取 N 个片段，强制召回结果来自多个不同文档，提升信息多样性。

## 让模型输出结构化结果

如果下游需要程序化处理答案（比如前端要高亮引用、要单独展示置信度），应当要求模型以 JSON 或固定标记格式输出，而不是自由文本。例如：

    请以如下 JSON 格式输出：
    {"answer": "答案正文", "citations": [1, 3], "sufficient": true}

配合模型的 JSON 模式（或 function calling），可以显著降低解析失败率。要注意的是，即使要求了 JSON，仍应对输出做容错解析——模型偶尔会在 JSON 外包裹解释性文字或 markdown 代码块标记。

## 上下文与成本

提示词的 token 数直接决定推理成本和延迟。一个粗略的换算：中文 1 个字约对应 1 到 1.5 个 token。若 top_k=5、每片段 500 字，参考资料部分约 2500 到 3750 token，加上系统指令与问题，单次请求的输入 token 在 3000 到 4000 之间。

在按 token 计费的云端 API 场景下，这个数字乘以日均查询量就是主要成本来源。因此**降低 top_k 或缩短切片长度都是直接的成本优化手段**——但必须以评测数据为依据，确认质量损失可接受，而不是拍脑袋压缩上下文。
