# 向量数据库选型：Chroma、FAISS、Milvus

向量存储层负责保存向量及其元数据，并对外提供相似度检索接口。常见方案可按"库"与"库函数"两类理解。

## ChromaDB

Chroma 是面向原型和中小规模的向量数据库，特点是开箱即用、API 简洁、与 LangChain 等框架集成度高。

- **优势**：`pip install chromadb` 后几行代码就能建集合；支持元数据过滤；有本地持久化模式；提供客户端／服务端两种部署形态。
- **局限**：官方明确定位为"AI 应用原型工具"，在超大规模（千万级以上）场景下性能与运维能力不及专用数据库。
- **易踩的坑**：**默认距离度量是 L2 而非余弦**。创建 collection 时应显式指定度量方式：

      client.create_collection(name="kb", metadata={"hnsw:space": "cosine"})

  若使用默认 L2，查询返回的 `distances` 是欧氏距离，把它当作相似度直接使用（例如取 `1 - distance`）会导致分数量纲错误。另一个常见问题是 `collection.get()` 默认不返回向量，需要显式传 `include=["embeddings"]` 才能取回，遗漏此项会得到空向量列表。

## FAISS

FAISS 是 Meta 开源的向量检索库，严格说是**库**而非数据库：它只做索引和检索，不负责数据持久化、元数据管理、增删改查事务、并发访问控制。

- **优势**：性能极强，索引类型丰富（Flat / IVF / HNSW / PQ 及其组合），支持 GPU 加速，是算法研究与大规模检索的事实标准。
- **代价**：需要自己实现元数据存储、id 映射、持久化（`write_index` / `read_index`）、以及删除时的 id 重建（`IndexIDMap` 配合 `remove_ids`）。生产系统里，FAISS 常作为"检索内核"被上层服务包装。

选择 FAISS 意味着接受"自己造数据库"的工程量；只有当性能或索引类型的需求超出现成数据库能力时才值得。

## Milvus

Milvus 是面向生产的分布式向量数据库，支持水平扩展、多副本、存算分离。

- **优势**：十亿级向量规模；丰富的索引类型；支持强一致性；有完整的监控与运维体系；提供 Zilliz Cloud 托管版。
- **代价**：架构复杂（依赖 etcd、对象存储、消息队列），本地部署资源开销大；对中小规模项目属于过度设计。

## 内存哈希表

最轻量的方案：用一个字典在进程内存里存 `id -> {vector, metadata}`，检索时暴力遍历算余弦。它不具备任何数据库能力——没有持久化、没有并发控制、重启即丢——但胜在零依赖、逻辑透明，适合单元测试、教学演示和链路验证。

它的另一个实用价值是作为**对照组**：当怀疑检索质量问题来自向量库的 ANN 近似或度量方式配置时，用内存精确检索跑一遍同样的评测集，就能判断是"库的问题"还是"数据/模型的问题"。

## 选型决策要点

按优先级排列的四个问题：

1. **数据规模**：十万级以内，内存方案或 Chroma 足够；千万级以上必须考虑 Milvus 或 FAISS + 自建服务。
2. **是否需要元数据过滤**：需要按时间、来源、权限等条件预过滤时，纯 FAISS 需要自行实现，数据库类方案原生支持。
3. **运维成本**：团队没有专职运维时，宁可选择单机方案，也不要为了规模提前引入分布式组件。
4. **数据量增长速度**：HNSW 类索引支持增量插入；IVF 类需要重新训练聚类中心，增量场景下需评估重建频率。

一个务实的结论是：**大多数企业知识库的规模在 10 万片段以内，Chroma 或单机 FAISS 完全够用**。把架构复杂度控制在数据规模之下，比盲目追求分布式更专业。
