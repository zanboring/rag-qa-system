# Ollama 本地大模型部署

Ollama 是一个本地大模型运行与管理的工具，把模型下载、量化版本管理、推理服务封装成简单命令，降低了本地部署的门槛。

## 基本使用

部署流程通常只有三步：

    # 1. 安装 Ollama 后启动服务
    ollama serve

    # 2. 拉取模型
    ollama pull qwen2.5:7b

    # 3. 交互测试
    ollama run qwen2.5:7b

服务启动后默认监听 `http://localhost:11434`，提供 HTTP API。

## 作为 OpenAI 兼容接口调用

Ollama 提供两种调用风格：

**原生 API**（`/api/chat`）：

    POST /api/chat
    {
      "model": "qwen2.5:7b",
      "messages": [
        {"role": "system", "content": "系统指令"},
        {"role": "user", "content": "用户消息"}
      ],
      "stream": false
    }

响应中答案位于 `message.content` 字段。`stream` 设为 false 时一次性返回完整结果；设为 true 则返回 SSE 流，适合需要逐字显示的前端。

**OpenAI 兼容接口**（`/v1/chat/completions`）：Ollama 同时实现了 OpenAI 的接口协议，这意味着任何基于 OpenAI SDK 写的代码只需把 base_url 指向 `http://localhost:11434/v1` 即可切换到本地模型。对已有代码的迁移成本极低，这是它被广泛采用的重要原因。

## 模型与硬件

模型规模直接决定硬件需求。7B 参数模型在 4-bit 量化下约占 4 到 5 GB 显存；13B 约需 8 到 10 GB；32B 及以上通常需要 24 GB 显存。若显存不足，Ollama 会回退到 CPU 推理，速度会下降一个数量级（从每秒几十 token 降到每秒几 token），此时交互体验明显变差。

中文场景常用模型：

- **qwen2.5:7b**：中文能力均衡，7B 规模下表现突出，是性价比很高的默认选择。
- **qwen2.5:14b / 32b**：质量明显提升，但对硬件要求更高。
- **glm4:9b**：智谱开源的本地版本，中文技术问答表现良好。

## 优缺点

**优点**

- **数据不出本地**：这是最核心的价值。处理企业敏感文档、个人隐私数据时，云端 API 往往因合规要求不可用，本地模型是唯一选项。
- **零调用成本**：模型下载后推理不再产生费用，适合高频调用或批量离线处理场景。
- **无速率限制**：不受 API 的 QPS 与 token 配额约束，可以自由做批量实验。
- **可离线**：内网、离线环境下依然可用。

**缺点**

- **效果弱于云端旗舰模型**：7B 级本地模型在复杂推理、指令遵循、长上下文处理上与云端大模型有明显差距。对 RAG 而言，最直接的体现是"依据资料作答"的约束遵循不够稳定，拒答倾向偏弱。
- **需要硬件投入**：要获得可用的推理速度，显卡是硬性门槛。
- **运维负担**：模型版本管理、服务常驻、并发请求排队都需要自己处理。

## 在 RAG 中的定位

本地模型在 RAG 系统里通常有两种用法：

1. **全链路本地化**：embedding、向量库、生成模型全部本地。适合对数据合规要求严格的场景。
2. **混合方案**：embedding 和向量库本地，生成用云端。或者反过来——生成用本地，只在需要高质量答案时才调云端。

务实的选择策略是：**先用本地小模型跑通链路和评测**，确认架构正确、检索质量达标后，再按需切换云端模型提升生成质量。因为 RAG 的效果瓶颈主要在检索，本地小模型足以暴露检索问题；反过来，如果检索本身有问题，换云端大模型也只是在一个错误的上下文上生成更流畅的错误答案。
