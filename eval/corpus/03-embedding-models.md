# Embedding 模型与向量化

Embedding 模型把文本映射成固定维度的高维向量，使语义相近的文本在向量空间中距离更近。它是 RAG 检索能力的来源——检索质量的上限由 embedding 模型的语义表达能力决定。

## 向量化的基本要求

一个合格的检索用 embedding 模型需要满足：

- **语义一致性**：同义不同形的文本（"怎么快速排序" 与 "快速排序的实现方式"）向量距离要近。
- **维度适中**：常见维度在 384 到 1024 之间。维度越高表达能力越强，但存储和检索开销线性增长。
- **归一化输出**：向量做 L2 归一化后，余弦相似度与点积等价，可以直接用内积加速检索。

## 中文场景的模型选择

中文检索任务上，BGE（BAAI General Embedding）系列是常用的开源选择。bge-small-zh-v1.5 输出 512 维向量，模型体积小，在消费级 CPU 上即可推理，适合中小规模知识库。bge-large-zh-v1.5 维度 1024，效果更好但需要 GPU 才实用。

使用 BGE 做检索时有一个关键细节：**查询需要加指令前缀**。bge 系列推荐给查询语句加上 "为这个句子生成表示以用于检索相关文章：" 这样的前缀，而文档侧不加。原因是这类模型在训练时对查询和文档采用了非对称编码，加前缀能让查询向量落到与文档向量匹配的空间位置。不加前缀会导致检索指标明显下降。

## 商业 API 与本地模型

除了本地开源模型，也可以调用商业 embedding API。优势是无需维护模型、效果稳定、支持多语言；代价是数据要出网、按量计费、有网络延迟。

选择依据主要是三条：

1. **数据合规**：涉及企业内部敏感文档时，本地模型往往是硬性要求。
2. **规模**：百万级以上的向量库，API 的调用成本和延迟会成为瓶颈。
3. **多语言**：需要跨语种检索时，商业模型的多语言能力通常更成熟。

## 零依赖的哈希 Embedding

在教学和单元测试场景中，常需要一个不依赖模型下载、结果确定的替代方案：**字符 n-gram 哈希**。做法是把文本拆成连续 n 个字符的片段（如 3-gram），每个片段哈希到固定维度的桶并累加计数，最后做 L2 归一化。

这种做法的本质是**词形匹配而非语义匹配**：共享大量字符 n-gram 的文本相似度高。它对同义改写的鲁棒性很差——"怎么排序" 和 "排序的实现方式" 虽然语义接近，但字符重叠有限，向量距离会偏远。

它的价值在于：无需下载模型、无需 GPU、结果完全可复现，因此适合做单元测试与链路验证。但用它跑出来的检索指标不能代表真实模型的效果，评测报告中必须区分标注，否则会得出错误结论。

## 维度与检索成本

向量库的存储开销可以用一个简单公式估算：

    存储字节数 ≈ 向量条数 × 维度 × 每维字节数

以 float32 为例，每维占 4 字节。10 万条 512 维向量约需 100000 × 512 × 4 ≈ 200 MB，内存完全放得下。若换成 1536 维、100 万条，则达到约 6 GB，此时就必须考虑量化压缩（如 int8 量化可降至 1/4）或磁盘索引。因此维度选择不只是效果问题，也是成本问题。
